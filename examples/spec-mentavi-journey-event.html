01. Executive

Executive and compliance summary

Problem

Mentavi’s patient portal writes lifecycle journey data into HubSpot Custom Behavioral Events (CBEs). Custom Behavioral Events are not expressly included in HubSpot’s Sensitive Data Covered Services. The live New User Journey event currently carries patient names, date of birth, and phone in plain text. That write path is not HIPAA-supportable.

Recommended architecture

Replace all Custom Behavioral Event writes with CRM-native records on HubSpot’s 2026-03 CRM Object APIs. The Journey Event is a CRM custom object. After cutover, records associate natively. No reversible patient identifier is stored as a property on the Journey Event.

1

Patient Portal

One patient action. Mentavi ensures a stable occurrence_id exists before send.

arrow_forward
2

Mentavi connector

Resolves the stored Contact Record ID. Three CRM writes. No events API.

arrow_forward
3

HubSpot CRM APIs

Contact / Deal properties plus one Journey Event record per occurrence. Current GA version: 2026-03.

verified What Mentavi is approving

  • Patient identity and PHI live only on the Contact, in Sensitive Data properties, under the BAA.
  • The Journey Event stores coded event types, timestamps, an opaque occurrence_id, and non-sensitive technical metadata.
  • The relationship to a patient lives in HubSpot’s native association layer, not in a Journey Event property.
  • All writes enter through the covered CRM path using a private app with Sensitive Data scopes.
  • Event type strings are coded or generic, never clinically descriptive.
  • No PHI appears in logs, errors, or unapproved stores. An approved Contact retry may resend the same patient fields. That retry stays inside Mentavi’s approved infrastructure.

help Open decisions for Mentavi legal

  1. Contact matching method (section 4). Recommendation: HubSpot Contact Record ID. Alternatives are in that section. This is not locked.
  2. Final Sensitive Data classification for each property in section 5. The table is proposed. Classification is irreversible once set.
  3. Coded event type naming: Option A (collapse) vs Option B (distinct opaque codes). RevPartners recommends Option B.
  4. Whether current patient-linked writes continue during Phase 1, and whether history-dependent automations may keep reading Custom Behavioral Event data. Corey is taking this to Mentavi compliance. It changes the activation gate, not the architecture.
  5. Whether occurrence_id stays a standard unique property (required for HubSpot-enforced upsert) or is classified Sensitive Data (Mentavi must de-dupe before the write).

Limitations

HubSpot’s BAA covers the platform when Mentavi is a covered entity or business associate. Mentavi’s current legal status with HubSpot is for Mentavi to confirm with counsel. This specification does not determine that status.

verified Documented sign-off

A written yes from Mentavi legal or compliance is the build gate. Email is enough.

Record who approved, their role, the date, and that they reviewed this specification (2 September 2026). Verbal-only does not count until that written confirmation follows.

03. Architecture

Target architecture and ownership

Three CRM writes per occurrence

1

Contact create or update

POST or PATCH /crm/objects/2026-03/contacts. Sensitive Data: names, DOB, phone, patient_type, address fields. Standard: lifecyclestage, attribution, current state. Store the returned Record ID.

2

Journey Event upsert

POST /crm/objects/2026-03/{objectTypeId}/batch/upsert with idProperty=occurrence_id. Coded event_type, occurred_at, UTMs, product metadata. No patient identifiers on this object.

3

Native association

PUT the default association Journey Event → Contact using the stored Record ID. See section 6 for the documented URL.

04. Identity

Identity, matching, and idempotency

verified Recommended pattern: Contact Record ID

  1. At email verification (or first Contact create), Mentavi calls POST /crm/objects/2026-03/contacts with identity data.
  2. HubSpot returns the Contact Record ID.
  3. Mentavi stores that ID against its user record.
  4. Every later Journey Event associates using that stored Record ID.
  5. Nothing patient-identifying is sent on the Journey Event payload: not email, user_pk, clientId, patientId, names, DOB, phone, or address.

Why: it is HubSpot’s native record identifier, minimum-necessary, and it avoids resending direct identifiers on every occurrence. It also sidesteps HubSpot’s hard constraint: Sensitive Data properties cannot enforce unique values. A Sensitive Data user_pk cannot be the unique Contact key.

Idempotency

Primary pattern. Mentavi ensures one stable occurrence_id (UUIDv4 or equivalent) exists before the Journey Event write. Never derived from a patient value. Stored as a unique standard property on Journey Event. Retries reuse the same occurrence_id. HubSpot’s documented upsert is batch upsert on that unique property, so a retry updates rather than duplicates.

Fallback, only if legal classifies occurrence_id as Sensitive Data. HubSpot cannot enforce uniqueness on a Sensitive Data property. Mentavi then checks for an existing row (or consults its own sent-events store) before the write. The architecture still works. HubSpot just stops being the duplicate lock. Compliance decides the classification.

A UUID is not automatically non-PHI. Mentavi legal decides. If occurrence_id cannot go in ordinary logs, Mentavi logs a separate correlation id (status, timestamp, event family, that correlation id). The UUID still goes to HubSpot. It does not go to Datadog / error text.

Display vs unique

These are two properties. They are not the same field.

  • Unique technical property: occurrence_id
  • Primary display property: display_label, written by the integration as [coded event_type] | [occurred_at]
  • Record card: event_type, occurred_at, event_family

A formatted display string is not a safe unique key. Two events of the same type can share a timestamp second. UUIDv4 does not.

Edge cases

ScenarioHandling
RetrySame occurrence_id, batch upsert, no duplicate. If legal classifies occurrence_id Sensitive Data, Mentavi de-dupes before the write instead.

08. Controls

Security and compliance controls

Minimum necessary

  • Only data required for the business purpose lands on each record.
  • PHI on Contact only. Journey Event holds coded types, timestamps, opaque IDs, attribution, and product metadata.
  • No PHI duplicated onto the occurrence record “for convenience.”

Property and portal configuration

lock Sensitive Data settings — Mentavi Super Admin only

In portal 21221632, RevPartners users are not Super Admins. Opening Settings > Security redirects to the user’s own account security page, not the portal Sensitive Data tab. HubSpot requires Super Admin to turn on or edit those settings.

A Mentavi Super Admin opens Settings > Security > Sensitive Data and confirms both of these before any Sensitive Data property is created:

  • Health/Medical Data
  • We are a HIPAA-covered entity or business associate

Once on, those settings are permanent. Categories cannot be removed. Until a Super Admin confirms this page, RevPartners cannot create Sensitive Data properties or verify that the setting is already enabled.

  • PHI properties: Sensitive Data classification, Health/Medical category, HIPAA / PHI checkbox where applicable.
  • Field-level access: restrict Sensitive Data visibility to authorized roles. Super Admins can still see the values.
  • Classification is permanent. An existing standard property cannot be marked Sensitive Data later, and a Sensitive Data property cannot be unmarked.

Auth, logging, retries

  • Private app with the scopes in section 6. Mentavi owns the app. If RP holds a token that receives PHI, Mentavi counsel decides whether RP is a business associate requiring its own BAA.
  • Logs, errors, monitoring: correlation id, HTTP status, timestamp, event_family. Log occurrence_id only if Mentavi classifies it as safe for ordinary logs. Never names, DOB, phone, email, address, user_pk, patientId.
  • Retries reuse occurrence_id. An approved Contact retry may resend the same patient fields inside Mentavi infrastructure. That is allowed. PHI in logs is not.

Open approvals

  • Mentavi compliance: architecture, before build.
  • Mentavi legal: matching method.
  • Mentavi compliance: Option A vs B coded types, and per-property Sensitive Data flags.
  • Mentavi and HubSpot: BAA applicability given current legal status.

Stated limitations

This document validates platform supportability. It is not legal advice. RP does not certify HIPAA compliance. HubSpot’s BAA covers the platform. Mentavi’s policies cover Mentavi’s use of it.
